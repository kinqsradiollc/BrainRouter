# 0.4.20 — Surfaces that tell the truth about their own state

> Status: **PROPOSED — planning only, awaiting owner approval.** No implementation begins until
> [ADR-028](../brainrouter-docs/decisions/ADR-028-stacked-pull-requests-done-properly.md) is
> approved.

## The question this release answers

> Four surfaces claim states they have not established — a stack that was never created, a steer
> that may never have arrived, a panel showing another session's work, and a planner that would
> present ten sources as one list without saying which are stale. What does it take for each to
> report only what it knows?

## Why now

0.4.19's D13 was written the day GitHub's preview was announced, from a changelog and an overview
page, before the CLI reference existed in our research. The model and the review integration are
sound. The part that touches GitHub is wrong in one specific and serious way: **`stack.addlayer`
opens an ordinary pull request and reports that it created a stack layer.**

## Delivery timetable

Sequential, single-track. The stacked-PR and receipt work (S rows) is a focused repair and lands
first; the planner (P rows) is a new persistence and sync layer.

| Week | Focus | Exit condition |
|---|---|---|
| **1** | S0–S2 — remove the lying action, capability detection, exit codes, create path | A layer is genuinely registered as a stack on GitHub |
| **2** | S3–S4 — navigation, sync/rebase, merge | A stack merges; the confirmation names every PR that lands |
| **3** | S5–S8 — auto-propose, receipts, artifacts panel | No surface claims a state it has not established |
| **4** | P0 — HLC, schema, migration | HLC survives adversarial clock-skew property tests |
| **5** | P1 — local store + outbox | Fully usable with the network off; outbox survives restart |
| **6** | P2-1, P2-2 — sync + LWW merge | Two devices converge on non-conflicting edits |
| **7** | P2-3, P2-4 — conflicts that must not auto-merge | Concurrent text loses nothing; delete-vs-edit asks |
| **8** | P3 — adapters + freshness | Six sources in one view, each showing its own age |
| **9** | P4 — planner and timetable | Today view and timetable usable end to end |
| **10** | P5 — agent, desktop, dashboard, retention | Same planner on two surfaces; agent proposes, never imposes |
| **11** | Multi-device soak | Offline edits on three devices reconciling without loss |

**Weeks 6–7 carry the real risk.** If merge semantics are wrong there, everything after moves.
Weeks 1–3 are well-understood repairs; weeks 8–10 are adapters and UI over a settled core.

**Week 11 is not padding.** Sync bugs surface under conditions unit tests do not reproduce — two
devices offline at once, an edit during a partial drain, a tombstone racing an edit. A week of
deliberate soak is cheaper than finding the same bugs by losing data.

## Owner decisions recorded

| Question | Answer |
|---|---|
| Agent may run `gh stack sync`? | **Yes, on explicit instruction** — never on its own inference |
| Auto-propose stacks? | **Yes**, gated to `shouldStack:true` and once per change |
| Merge queue | **Wait for GitHub's native queue** — no third-party integration |

## Explicitly out of scope

- **A Trunk-specific merge-queue integration.** Waiting for GitHub's first-party support.
- **Reimplementing cascading rebase.** GitHub maintains it; ours would be a worse copy.
- **Cross-fork stacks.** Not supported by the platform.
- **Auto-merging a stack without confirmation**, however green the checks.
- **A local stack database.** `gh stack` owns local tracking; a second store would drift.
- **A "read" receipt that turns green on context inclusion.** Attention is not instrumentable; a
  receipt we cannot substantiate is worse than none.

## Non-negotiables

- `stack.addlayer` is removed before it is replaced. An action that reports success for work it did
  not do gets no deprecation window.
- History rewriting of branches under review is never agent-initiated without explicit instruction,
  and every run previews the layers it will rewrite.
- Auto-propose fires once per change and never for an indivisible one. A proposal that fires often
  is one that gets dismissed reflexively, and then it is worth nothing when it matters.
- A stack merge confirmation names **every** pull request that will land, not only the one asked for.
- Capability is detected, not assumed; where the extension is absent, stack actions are hidden
  rather than offered-and-failing.
- A message never shows "read". It shows `delivered` — what we can prove — and `acknowledged` only
  on evidence the agent consumed it. A dropped steer is always loud.
- The artifacts panel never shows another session's work while claiming to show yours, and a
  multi-session view always attributes each artifact to its source session.
