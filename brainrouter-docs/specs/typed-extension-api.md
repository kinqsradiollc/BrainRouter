# Spec: Typed Extension API + Audited Self-Update for the BrainRouter Agent

Status: Proposed
Owner: Core / Agent
Scope: `packages/core`, `brainrouter-cli`, `brainrouter-desktop`

This spec defines two native BrainRouter capabilities that close the gap between
our static, declarative customization surface and a programmable one:

1. A **typed extension API** — a hot-loadable TypeScript module that can register
   agent tools, providers, lifecycle hook handlers, and UI affordances against
   the existing core registries, without forking the harness.
2. An **audited self-update path** — turning today's notice-only update check
   into a trust-gated, dependency-audited install flow.

Both are framed entirely in BrainRouter terms and build directly on our existing
registries (`packages/core/src/tool/registry.ts`,
`packages/core/src/tool/executors.ts`,
`packages/core/src/provider/providers/index.ts`,
`packages/core/src/hooks/hooksStore.ts`,
`packages/core/src/pack/packs.ts`).

---

## Feature 1 — Typed Extension API (P0, highest leverage)

### Goal

Today a user can customize BrainRouter declaratively: agent definitions and
commands ship in **packs** (`packages/core/src/pack/packs.ts`), behavior guards
ship as **markdown hookify rules** (`packages/core/src/hooks/hookifyStore.ts`)
and **shell lifecycle hooks** (`packages/core/src/hooks/hooksStore.ts`), and
tools are a fixed set in `packages/core/src/tool/registry.ts`. There is no
in-process, code-level extension point: you cannot add a new agent tool, register
a provider, or attach a typed lifecycle handler without editing core.

The Extension API adds exactly that: a single typed entrypoint that an extension
module exports, called once at agent startup, that receives a typed
`ExtensionHost` and uses it to register tools, providers, hook handlers, and (in
desktop) panels. Extensions resolve at the same three tiers packs already use
(built-in > user > workspace) and are governed by the same project-trust gate as
self-update (Feature 2), so untrusted code never auto-loads.

### Why it matters for our agents

Our autonomous agents are constrained to the tool surface generated by
`registryAllowedTools()`. An extension lets a workspace author add a
domain-specific tool (e.g. `run_migration`, `query_warehouse`) that the agent can
call within the same access-tier and parallel-safety model as native tools — no
core change, no republish. It also lets us register a new OpenAI-compatible
provider with custom streaming/auth in code rather than only via
`providers.json`.

### Design

#### New module: `packages/core/src/extension/`

```
packages/core/src/extension/
  manifest.ts        // ExtensionManifest type + discovery (mirrors pack/packs.ts tiers)
  host.ts            // ExtensionHost interface — the typed registration surface
  loader.ts          // resolve → trust-gate → import() → activate; collects registrations
  registry.ts        // in-memory ExtensionRegistry: aggregates contributed tools/providers/hooks
  index.ts
```

#### Manifest + discovery (`manifest.ts`)

Reuse the pack tier model verbatim. An extension is a folder containing
`extension.json` plus an entry module (default `index.ts`/`index.js`):

```ts
export interface ExtensionManifest {
  name: string;
  version?: string;
  description?: string;
  /** Entry module relative to the extension folder. Default 'index.js'. */
  main?: string;
  /** Capabilities the extension declares it will register (for the trust prompt). */
  contributes?: Array<'tools' | 'providers' | 'hooks' | 'panels'>;
}
```

Discovery mirrors `packs.ts`:

```
built-in   <cli>/extensions/<name>/
user       ~/.config/brainrouter/extensions/<name>/
workspace  <workspace>/.brainrouter/extensions/<name>/
```

with the same `SOURCE_RANK` precedence (workspace shadows user shadows built-in).
Enable/disable state lives alongside pack state in a small `extensionStore.ts`
(same shape as `packStore.ts`).

**Name validation (required, security-critical — CWE-22).** `<name>` comes from a
directory name / an `extension.json` that a workspace or user directory can supply,
and it is interpolated into a filesystem path that is then `import()`ed in-process
with full host capabilities. The loader **MUST** reject any name that is not a
single safe path segment — enforce `^[a-z0-9](?:[a-z0-9-]*[a-z0-9])?$` (lower-kebab,
no dots, slashes, or `..`) **before** constructing the path, and additionally verify
the resolved absolute path stays inside the intended `extensions/` root (realpath
containment). A name like `../../evil` or `../steal-config` must never resolve or
load — otherwise a malicious repository checkout could achieve arbitrary module
execution (RCE). Built-in extension names are fixed constants and are exempt from
discovery-time inference but still pass the same validator.

#### The typed host (`host.ts`)

```ts
import type { LocalToolExecutor } from '../tool/executors.js';
import type { ProviderDefinition } from '../provider/providers/definition.js';
import type { HookEvent } from '../hooks/hooksStore.js';

export interface ExtensionHookHandler {
  event: HookEvent;
  match?: string; // substring match on tool name, like Hook.match
  /** Return 'deny' to block (pre-tool / user-prompt-submit), else undefined. */
  handle(ctx: ExtensionHookContext): Promise<'deny' | void> | 'deny' | void;
}

export interface ExtensionHost {
  /** Register an agent tool. Goes through the SAME access-tier + parallel-safe
   *  contract as native tools (LocalToolEntry). */
  registerTool(entry: {
    executor: LocalToolExecutor;
    accessTier: import('../exec/execPolicy.js').AccessMode;
    actionKind: import('../exec/execPolicy.js').ActionKind;
    parallelSafe: boolean;
  }): void;

  /** Register an OpenAI-compatible provider definition in code. */
  registerProvider(def: ProviderDefinition): void;

  /** Attach a typed lifecycle handler (in-process analogue of a shell hook). */
  registerHook(handler: ExtensionHookHandler): void;

  /** Structured logger scoped to the extension name. */
  readonly log: (msg: string, fields?: Record<string, unknown>) => void;

  /** Read-only context the extension may key off of. */
  readonly workspaceRoot: string;
  readonly version: string;
}

/** The single entrypoint an extension module must export. */
export type ExtensionActivate = (host: ExtensionHost) => void | Promise<void>;
```

An extension's entry module exports `activate`:

```ts
// <workspace>/.brainrouter/extensions/warehouse/index.ts
import type { ExtensionActivate } from '@kinqs/brainrouter-core/extension';
export const activate: ExtensionActivate = (host) => {
  host.registerTool({ executor: queryWarehouseExecutor, accessTier: 'read', actionKind: 'network', parallelSafe: true });
};
```

#### Loader (`loader.ts`)

1. Discover manifests across the three tiers (`manifest.ts`).
2. Filter to **enabled AND trusted** (Feature 2's `trust.ts` project-trust gate).
   An extension in an untrusted workspace is listed but NOT activated; the CLI
   prints a one-line "extension X present but workspace not trusted — run
   `brainrouter trust`" notice.
3. Dynamically `import()` the entry module. TS entries are supported via the
   CLI's existing TS runtime (the CLI already runs as TS); for built distribution
   we resolve `dist/index.js`. No new transpiler dependency in core — core loads
   the compiled `main`; the CLI dev path may load `.ts` through its own loader.
4. Construct one `ExtensionHost` per extension, call `activate`, and collect
   every registration into the `ExtensionRegistry`.
5. Activation is fault-isolated: a throwing `activate` is logged and skipped; it
   never aborts agent startup.

#### Registry merge (`registry.ts`)

`ExtensionRegistry` exposes:

- `tools(): LocalToolEntry[]` — appended to `LOCAL_TOOL_REGISTRY` consumers.
- `executors(): LocalToolExecutor[]` — merged into the executor lookup used by
  `Agent.executeLocalTool` (`packages/core/src/agent/agent.ts:2991`).
- `providers(): ProviderDefinition[]` — appended after `BUILTIN_PROVIDERS` in the
  catalog merge (`packages/core/src/provider/catalog.ts`), with the same
  precedence rule built-ins already enforce (built-in id wins).
- `hookHandlers(event): ExtensionHookHandler[]` — invoked at the existing hook
  fire points alongside shell hooks.

#### Hook points to change (minimal, additive)

| Surface | File | Change |
|---|---|---|
| Tool exposure | `packages/core/src/tool/registry.ts` | `registryAllowedTools(mode)` / `registryParallelSafeLocal()` union with `ExtensionRegistry.tools()` filtered by tier. Registry array itself stays static; a new `effectiveToolRegistry()` returns native+extension entries. |
| Tool execution | `packages/core/src/agent/agent.ts` (`executeLocalTool`, ~line 2991) | If no native executor matches, look up an extension executor before falling through to `executeLocalToolLegacy`. |
| Tool specs | `packages/core/src/tool/specs.ts` (`LOCAL_TOOLS`) | Spec list the model sees is `LOCAL_TOOLS` ∪ extension `executor.spec()`. |
| Provider catalog | `packages/core/src/provider/catalog.ts` (`buildProviderCatalog`) | Insert extension providers between built-ins and `providers.json` entries. |
| Lifecycle hooks | wherever shell hooks fire today (the `hooksStore` consumers) | After running shell hooks for an event, run `ExtensionRegistry.hookHandlers(event)`; a `'deny'` from a `pre-tool`/`user-prompt-submit` handler blocks identically to a non-zero shell-hook exit. |

#### Integration with existing systems

- **Hooks/skills**: extension hook handlers are a typed, in-process sibling of
  shell hooks (`hooksStore.ts`) and markdown hookify rules (`hookifyStore.ts`) —
  same events, same deny semantics. Skills and packs are unchanged; an extension
  can be *shipped inside a pack* (add an `extension/` subdir to the pack folder;
  `packs.ts` already enumerates pack subdirs).
- **Providers**: identical `ProviderDefinition` contract as
  `providers/index.ts`; nothing about model discovery changes (models still come
  from the endpoint's `/models`, never hardcoded).
- **Sandbox**: extension tools that map to shell/exec action kinds route through
  the same `execPolicy` / `sandbox.ts` path — an extension cannot bypass the
  access tier or sandbox; it can only register a tool *at* a tier.

### Phased steps

- **Phase 1 — discovery + types (no activation).** Add `manifest.ts`,
  `host.ts`, `registry.ts` skeleton, `extensionStore.ts`. `brainrouter ext list`
  CLI command shows discovered extensions and their tier/enabled/trusted state.
  No code is executed yet.
- **Phase 2 — tool contributions.** Implement `loader.ts` activation, wire
  `registerTool` → `ExtensionRegistry` → `effectiveToolRegistry()` and the
  `executeLocalTool` fallthrough. An example built-in extension contributes one
  read-tier tool end-to-end.
- **Phase 3 — provider + hook contributions.** Wire `registerProvider` into
  `buildProviderCatalog` and `registerHook` into the lifecycle fire points.
- **Phase 4 — desktop surface.** Add `registerPanel` to the host and a
  `brainrouter-desktop/src/panels/` mount point; list/enable/disable extensions
  in `brainrouter-desktop/src/settings.tsx`.

### Test expectations (TDD — write first)

New tests under `packages/core/src/tests/`:

- `extension-discovery.test.ts` — tier precedence (workspace shadows user shadows
  built-in), malformed `extension.json` ignored, disabled excluded.
- `extension-loader.test.ts` — a throwing `activate` is isolated (other
  extensions still load); an untrusted-workspace extension is discovered but NOT
  activated.
- `extension-tool-merge.test.ts` — a contributed read-tier tool appears in
  `effectiveToolRegistry()` for read mode and is hidden below its tier; an entry
  whose `actionKind` disagrees with its `accessTier` fails the same guard that
  `tool-registry.test.ts` already enforces.
- `extension-provider-merge.test.ts` — contributed provider appears after
  built-ins, and a built-in id still wins over a colliding extension id.
- `extension-hook-deny.test.ts` — a `pre-tool` extension handler returning
  `'deny'` blocks the call exactly like a non-zero shell-hook exit.

All new code follows our import-order/type-annotation conventions and ships with
the guard test green before merge.

## Feature 2 — Audited Self-Update + Project Trust (P1)

### Goal

Today `brainrouter-cli/src/runtime/updateCheck.ts` only prints a "you're N
versions behind" notice (via `npm view`); there is no audited install, no
project-trust gate, and nothing prevents an extension/pack from running arbitrary
code in an untrusted workspace. This feature adds:

- A **project-trust file** (`trust.json`) gating execution of any in-workspace
  code (extensions, pack hooks).
- An **audited update** command that surfaces what would change and runs a
  dependency audit before installing, instead of a passive notice.

### Why it matters for our agents

Autonomous agents operate unattended in arbitrary checked-out repos. A typed
extension API (Feature 1) is only safe if untrusted workspace code cannot
auto-activate. The trust gate is the prerequisite that makes Feature 1 shippable;
the audited update gives operators a credible supply-chain story for the agent
binary itself.

### Design

#### New module: `packages/core/src/trust/trust.ts`

```ts
export interface TrustEntry { workspaceRoot: string; trustedAt: string; trustedBy?: string; }
export function isWorkspaceTrusted(workspaceRoot: string): boolean;
export function trustWorkspace(workspaceRoot: string): TrustEntry;
export function revokeWorkspace(workspaceRoot: string): boolean;
```

Trust is stored per-user at `~/.config/brainrouter/trust.json` (NOT in the
workspace — a repo cannot trust itself). `isWorkspaceTrusted` is the gate
Feature 1's loader calls before `import()`.

#### Audited update (`brainrouter-cli/src/runtime/updateCheck.ts` + new `updateApply.ts`)

- Keep `compareSemver` / `formatUpdateBanner` (already pure + tested).
- Add `auditUpdate()`: before offering an install, run the package manager's
  audit and parse the result into a small `{ critical, high, summary }` shape;
  the CLI refuses to auto-install when `critical > 0` and instead prints the
  advisory.
- Add an explicit `brainrouter update` command (no silent background install) —
  fire-and-forget *checking* stays as-is; *applying* is always user-initiated.

#### Integration

- The trust gate is consumed by Feature 1's `loader.ts` and by pack-hook
  execution in `packs.ts` consumers.
- Update flow reuses the existing throttled cache in `updateCheck.ts`.

### Phased steps

1. `trust.ts` + `~/.config/brainrouter/trust.json` + `brainrouter trust` /
   `brainrouter trust --revoke` CLI commands.
2. Gate Feature 1's loader and pack-hook execution on `isWorkspaceTrusted`.
3. `auditUpdate()` + `brainrouter update` command with the critical-vuln refusal.

### Test expectations (TDD — write first)

- `trust-store.test.ts` — trust/revoke round-trip; an untrusted workspace returns
  `false`; trust file is per-user, not per-workspace.
- `update-audit.test.ts` — `auditUpdate` parses a sample audit payload; a
  `critical > 0` result blocks auto-install and yields the advisory string.
- Extend `update-check.test.ts` to cover the new explicit-apply path stays
  user-initiated (no silent install).

## Out of scope

VM/container-isolated execution beyond today's `sandbox-exec`/`bwrap` layer, and
any change to model/provider discovery (models continue to come from the
endpoint's `/models`). Those are tracked separately.
